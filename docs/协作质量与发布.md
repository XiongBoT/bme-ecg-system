# 协作质量与发布

所有成员可修改所有模块。每人使用自己的克隆，每个任务使用独立分支；主分支通过 PR 集成。

## 自动检查

`.github/workflows/quality.yml` 在面向 main 的 PR、main 推送和手动触发时运行；协作流程建设分支也会触发验证。工作流只读仓库、不使用生产凭据，不连接实物、不部署。

| 检查 | 内容 |
| --- | --- |
| Repository policy | 已跟踪文件中的常见私密/生成路径、私钥块和 Python 语法；只输出路径与问题类型 |
| Python (pi) | Python 3.12、NumPy/SciPy、串口/PDF依赖与中文报告字体；虚拟显示下运行树莓派测试 |
| Python (cloud) | 独立进程运行云端测试，覆盖账号、设备、记录、任务和研究工具 |
| Algorithm evaluation tests | 独立安装 WFDB、NeuroKit2、ts2vg；验证匹配、分类分母、真实候选适配器和报告；发现零用例或任何跳过都不通过，不下载公开数据库 |
| Web tests | Node.js 22 运行所有前端回归测试 |
| Windows package | Windows 下编译桌面启动器并验证归档白名单和校验值 |
| Android package | APK 资源/权限测试、Java 地址与导出策略测试，使用临时 CI 密钥编译和验证 APK |
| Quality gate | 所有前置任务必须成功；失败、取消或整个任务跳过均不通过 |

路径检查不能识别所有形式的秘密或真实心电数据，提交前仍需人工检查。单元测试自身标记的 skip 会出现在日志中，评审者必须确认原因；Windows 专属构建由单独任务覆盖。

本地复跑：

```powershell
python -m unittest discover -s tools -p test_repository_policy.py -v
python tools/check_repository.py
python tools/run_checks.py --suite pi
python tools/run_checks.py --suite cloud
python tools/run_checks.py --suite web
```

Android 工作流只用运行器中的临时密钥构建测试包，不上传或发布该包；正式签名密钥不进入 PR 工作流。固件当前仍使用 Keil，改动必须提供编译结果和需要的实物证据；CI 通过不等同手机、硬件或临床验证。

## main 的保护目标

在 GitHub Settings → Branches 或 Rules → Rulesets 中设置 main：

| 保护项 | 要求 |
| --- | --- |
| 合并入口 | 必须通过 PR，不能直接推送 main |
| 最终审核与合并 | 由 XiongBoT 审核并决定合并；规则集仅允许该账号通过 PR 更新 main |
| 其他成员批准 | 最少批准人数为 0；不强制其他成员批准，不设置 CODEOWNERS 或按目录指定批准人 |
| 自愿提交的批准 | 保留 `Dismiss stale pull request approvals when new commits are pushed`，避免把旧意见当作针对新差异的意见；不增加批准人数门槛 |
| 自动检查 | 必须通过 GitHub Actions 产生的 `Quality gate`，并开启分支必须与 main 同步 |
| 审查讨论 | 全部解决后才能合并 |
| 历史和权限 | 禁止强推、禁止删除 main，管理员也遵守保护 |

`Require approval of the most recent reviewable push` 保持关闭。成员可以给任何模块提出审查意见；没有其他成员批准不阻止 XiongBoT 在检查通过后决定合并。

规则集 [main-owner-final-review](https://github.com/XiongBoT/bme-ecg-system/rules/28057558) 仅匹配 `refs/heads/main`，开启 `Restrict updates`，唯一例外为 `XiongBoT`（User ID `92081851`），方式为 `For pull requests only`。规则集负责限制谁可以合并；原有分支保护继续要求 PR、Quality gate、同步 main 和解决讨论，即使 XiongBoT 也不能直接推送 main 或跳过这些保护。其他成员仍可推送任务分支并提交 PR。

最终审核以 XiongBoT 核对当前差异和测试证据后亲自决定合并为准，不额外要求先点 GitHub 的 Approve。代理只能准备修改、验证和 PR；合并前须取得用户对 PR 当前 HEAD 提交的明确确认并记录该 SHA，合并请求必须以该 SHA 为前置条件。新增提交使原确认失效，须重新确认；不能将自查、AI 复核、测试通过或一般开发授权视为该确认。

先运行工作流，使 Quality gate 出现在可选检查列表，再将其设为必需检查。不要写一个从未实际产生的检查名而把所有 PR 永久锁住。是否生效以 GitHub 设置和 PR 合并栏为准，本文件不是生效证明。

变更记录：2026-11-24 取消强制他人批准；2026-11-25 曾恢复 1 人门槛，同日按用户最新要求取消，并改为由 XiongBoT 最终审核和合并。自动检查、同步、讨论解决、禁止强推/删除和管理员约束保留。

GitHub 强制检查账号权限和合并条件，不能判断一个人是否实际读懂代码；XiongBoT 仍需核对差异与证据。Issue 中的修改范围、临时协调顺序以及 PR 是否混入无关工作由审查者核对；模板和说明不会自动锁文件，也不能保证零冲突。外部贡献的工作流若显示“等待批准”，表示尚未运行，不等于检查成功；有权限成员核对工作流和代码后再决定是否批准运行，批准运行不等同最终同意合并。

## AI 与人工审查

`.github/copilot-instructions.md` 提供统一的 AI 审查关注点。它不等于已订阅或启用自动 AI 审查。已有 Copilot 权益时可在 PR 请求其审查；启用自动审查前核对账户权益与费用。也可将已去除凭据/个人数据的代码差异交给已授权的 AI 工具。

提交者核对测试证据、接口影响、关键业务行为和部署风险，也可邀请其他成员复核。AI 的建议必须验证；AI 无意见不代表检查通过或授权自动合并。测试和审查不自动操作服务器、STM32 或树莓派。

## 云端统一部署

采用“成员提交 PR → XiongBoT 审核合并 → XiongBoT 准备准确版本的部署包 → 备份与统一部署 → 记录验证结果”的流程。合并不自动上线；源码包准备成功也不表示服务器已更新。

| 角色 | 工作范围 | 需要的权限 |
| --- | --- | --- |
| 项目成员 | 本机开发与测试、推送任务分支、提交 PR、对任何模块提出修改和审查意见 | 本人的 GitHub 账号及仓库写入权限 |
| XiongBoT | 最终审核与合并、选择上线版本、安排维护时间、备份、部署、验收和回退 | 仓库管理权限、自己的腾讯云及服务器管理权限 |
| GitHub Actions | 检查源码、准备可追溯的部署包 | 仓库内容与运行记录只读；无服务器凭据 |

成员不用共享腾讯云主账号、`ubuntu` 密码、SSH 私钥或设备上传密钥。成员需要调试时在本机运行独立服务，使用模拟或获准的公开数据；需要线上排查时向 XiongBoT 提供复现步骤，由负责人查看必要日志并去除账号、凭据和心电内容后反馈。GitHub 写入权限不代表拥有服务器登录权限。

### 准备部署包

工作流文件为 [cloud-release.yml](../.github/workflows/cloud-release.yml)，校验入口为 [prepare_cloud_release.py](../tools/prepare_cloud_release.py)。它只接受手动触发，没有 push、PR 或定时部署入口。

1. XiongBoT 审核并合并 PR，等待 **main 上该提交**的 `Project quality` 检查成功。PR 分支的检查通过不能代替合并后主分支检查。
2. 在 GitHub 的 main 提交页复制完整 40 位 SHA。打开 Actions → **准备云端部署包** → Run workflow，分支选择 **main**，填写该 SHA。
3. 入口核对原始发起人及重跑人均为 XiongBoT、运行分支为 main、填写版本等于运行版本及当前 main，并核对该 SHA 最新的 `quality.yml` 主分支推送检查已成功。版本已变化、检查未结束或失败时停止，重新核对版本和检查后再发起。
4. 运行成功后下载 `cloud-source-完整SHA` 附件并解开外层归档，得到以下文件。附件保留 **7 天**；要长期保留时由负责人保存到自己的发布资料目录，不提交回 Git。

| 文件 | 用途 |
| --- | --- |
| `ecg-cloud-linux.zip` | 原有明确白名单产生的云端源码包，含现有模型相关文件，不包含运行数据、配置凭据和虚拟环境 |
| `ecg-cloud-linux.zip.sha256` | 整个源码包的 SHA256 |
| `MANIFEST.sha256` | 包内各文件的 SHA256 |
| `release-source.json` | 来源提交、操作者、工作流与质量检查运行、包和清单摘要；状态为 `prepared-not-deployed` |

只使用本仓库 **main 上由 XiongBoT 发起**的运行结果。附件名称和来源文件本身不能证明可信，应同时核对 GitHub 上的工作流链接、提交和操作者。工作流不保存服务器密码或密钥，不连接 SSH，不调用历史自动覆盖脚本，也不把打包记录登记为生产环境部署。

### 在云端统一更新

1. 由 XiongBoT 确认此次上线版本、维护时间及影响范围，暂停新增测量，核对仍在进行的上传、分析及维护任务。成员不直接上传文件覆盖服务目录。
2. 按[部署与升级](../心电云端平台/docs/部署与升级.md#部署前记录)保存并校验程序、配置、模型和完整数据备份；明确旧版本及数据兼容的回退方法。
3. 将已核验的源码包交给服务器上的既有升级流程。比对整包摘要与包内清单，先在隔离数据副本验证，再按当前实例的实际路径切换服务。不要把首次安装命令或历史升级脚本直接用于现有服务。
4. 验证服务健康、账号隔离、网页、终端上传以及本次修改的功能。需要设备联调时另行记录实际设备结果；本地软件测试不能替代它。
5. 将结果登记到[版本与交付状态](版本与交付状态.md)，安装包发布及更新清单按相应流程单独处理。失败时按预案恢复程序，保留升级后新收到的数据。

每次发布至少记录：**负责人、时间、来源 PR/完整 SHA、包 SHA256、原版本、备份和回退位置、实际验证结果、未完成项**。备份路径和含账号的日志保存在负责人的私有运维记录中，公开 Issue/PR 只放去除敏感内容的结果。

2026-11-26 核对：main 已有所有者专属 PR 合并规则、必需 Quality gate、同步主分支和讨论解决要求；强推、删除及自动合并均关闭；Actions 默认只读且不能代批 PR；仓库级 Actions secrets 与 deploy keys 均为空。本次核对不证明腾讯云子账号、Linux 登录账号或已有服务器密钥已受限，这些需在负责人登录云端后另行核验。

若以后接入自动部署，应另行审查部署流程并为服务器凭据配置仅负责人可批准的环境；当前课程项目沿用上述手动统一部署方式，无需增加服务器或共享管理员账号。

## 版本与回退

1. 每个 PR 聚焦一个问题，提交说明描述行为变化，不混入无关工作。
2. 发布从通过检查的 main 提交创建标签，示例：系统 `v1.1.0`，桌面 `desktop-v1.2.0`，安卓 `android-v1.0.1`。版本只是示例，不代表已经发布。
3. 在发布说明记录提交 SHA、各组件版本、兼容协议/数据格式、测试来源、未验收项目、包 SHA-256、升级前版本和回退步骤。安装包作为 Release 附件，不加入 Git 源码。
4. 服务器、树莓派和固件分别登记已部署的提交/包版本；合并与部署分开。发布前保存必要的数据备份，数据库变更明确迁移与回退兼容性。
5. 撤销代码用新建修复 PR 或 git revert 保留历史，不用强推公共分支。回退应用不得覆盖回退期间新增的心电记录。

原工作目录若有未提交改动，先在其所属任务分支妥善提交或另存，再同步 main；不要直接 reset/clean 或整目录覆盖。
