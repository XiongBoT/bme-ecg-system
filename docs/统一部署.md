# 心电云端与心伴统一部署

统一的是交付来源：心电云端、心伴后端和心伴生产前端使用同一完整 Git SHA。两个服务仍保留独立进程、依赖环境、账号和数据库。Android、Windows、树莓派和 STM32 的发布另行登记，不能因云端打包成功而标为已更新。

## 选择经过检查的版本

负责人合并 PR 后，等待该 **main 提交**的 `Project quality` 成功，再在 Actions 的“准备云端部署包”工作流选择 main，输入完整 40 位 SHA。工作流核对所有者、最新 main 和对应质量检查，使用锁文件安装前端依赖、构建 `/heartlife/` 页面，再打包。工作流没有服务器凭据，不自动部署。

下载 `cloud-source-完整SHA` 附件并解开外层归档。统一部署使用以下三份文件，原有 `ecg-cloud-linux.zip` 等文件继续提供单模块兼容交付：

| 文件 | 内容 |
| --- | --- |
| `ecg-system-linux.zip` | 三个组件、迁移脚本、运行模板及本说明 |
| `ecg-system-linux.zip.sha256` | 整包 SHA256 |
| `system-release-source.json` | main 提交、操作者、构建与质量检查链接，以及整包和清单 SHA256 |

附件保留 7 天，负责人需及时保存。先在 GitHub 核实工作流来源、操作者、SHA 和检查结果，再核对来源 JSON 与整包摘要。仅有一个同名文件或 JSON 声明不足以证明来源可信。

归档的 `ecg-system/` 目录内：

| 路径 | 用途 |
| --- | --- |
| `ecg-cloud/` | 现有白名单中的心电 API、管理页面及模型文件 |
| `heartlife/backend/` | 心伴 API、依赖声明、Alembic 配置及迁移 |
| `heartlife/frontend/dist/` | 已构建的生产页面及 `release-source.json` |
| `heartlife/scripts/migrate.py` | 心伴数据库迁移入口 |
| `heartlife/deploy/tencent-cloud/` | systemd 和同站点 Nginx 子路径模板 |
| `RELEASE.json` | 三个组件的共同源码 SHA；状态 `prepared-not-deployed` |
| `MANIFEST.sha256` | 包内文件清单及摘要；清单自身不自包含 |
| `DEPLOYMENT.md` | 本说明的包内副本 |

不包含真实配置、账号数据、记录、虚拟环境、Node 依赖或 APK。前端已经构建，服务器无需重新安装 Node 或编译页面。源码 SHA 不代替运行环境记录；上线时仍需记录 Python 版本和实际安装依赖。

## 部署前核对与备份

1. 核实目标实例和运行账号，读取现行 systemd 单元、程序目录、数据目录、环境文件和 Nginx 配置。不要将文档中的默认路径当作服务器实际路径。
2. 记录旧版本、服务状态及端口，安排维护窗口；确认没有进行中的测量、未完成上传或后台维护任务。
3. 在服务器私有运维目录保留旧程序、环境文件、服务单元、Nginx 配置、模型及两套完整数据备份。SQLite 使用其备份接口，或在停止对应服务后制作一致副本；运行时直接复制主数据库文件可能漏掉 WAL 数据。
4. 实际检查备份可读取、可校验，明确新旧程序和数据库的兼容性。迁移后不能仅切换旧程序就假定能够回退。

先验证归档，再解压到**新的、尚不存在的版本目录**，不要覆盖当前程序或数据目录。以下校验命令分别在外层附件目录和解压后的 `ecg-system/` 目录执行：

```sh
sha256sum -c ecg-system-linux.zip.sha256
# 解压到新的版本目录后，在其中的 ecg-system/ 目录运行：
sha256sum -c MANIFEST.sha256
```

核对 `RELEASE.json`、`system-release-source.json` 和 `heartlife/frontend/dist/release-source.json` 的 SHA 相同，前端 `base_path` 为 `/heartlife/`。部署前清单应完整通过；后续产生的虚拟环境和缓存不属于清单。

## 配置与隔离验证

在新程序下分别创建 Python 3.12 环境。心电云端使用 `ecg-cloud/requirements.txt`，需要现行模型与 QRS/RR 分析时同时安装 `requirements-model.txt`；心伴使用 `heartlife/backend/requirements.txt`。保留各自环境，不混装依赖。

生产配置和数据置于版本目录之外，权限只向对应运行账号开放。不要直接将 `.env.example` 作为生产配置，也不要执行包内旧的首次安装脚本覆盖现行单元。

| 配置 | 统一部署要求 |
| --- | --- |
| 心电 `ECG_DATA_DIR` | 现行心电数据的绝对路径；隔离验证时改用专门副本 |
| 心伴 `DATABASE_URL` | 现行心伴数据库的绝对 SQLite URL；隔离验证时使用另一份副本 |
| 心伴 `COOKIE_PATH` | `/heartlife/`，与构建子路径一致 |
| 心伴 `COOKIE_SECURE` / `DEMO_MODE` | HTTPS 生产环境分别为 `true` / `false` |
| 心伴 `FRONTEND_ORIGIN` | 实际 HTTPS 站点来源，不带 `/heartlife/` 路径 |
| 心伴 `ECG_API_BASE_URL` | 同机生产实例通常为 `http://127.0.0.1:8766`；隔离验证改为测试实例端口 |
| 心伴 `ECG_EXTERNAL_URL` | 真实心电 HTTPS 入口 |
| 心电 `ECG_HEARTLIFE_URL` | 同一 HTTPS 站点下的 `/heartlife/` |
| 两端集成密钥 | 心电 `ECG_HEARTLIFE_CLIENT_SECRET` 与心伴 `ECG_CLIENT_SECRET` 相同且至少 32 字符；只在服务器私有配置保存 |

没有集成配置时维持现有独立使用方式，不在部署过程中自动创建用户、绑定或测量授权。

先用两套隔离数据和空闲回环端口运行，禁止两个版本同时操作同一数据库。心伴进程启动时执行迁移；也可从 `heartlife/backend/` 使用同一环境变量运行 `../.venv/bin/python ../scripts/migrate.py`。迁移命令必须显式加载与待验证实例一致的环境，不能因缺少 `DATABASE_URL` 而意外创建默认数据库。隔离实例不得连接生产心电 API、终端或外部助手服务。

核对心电 `/health`、心伴 `/api/v1/health`、前端入口及静态文件。用专用测试账号验证账号隔离、只读绑定、另行授权的固定时长测量及私密周报；没有设备时仅记录软件验证，不能登记实测成功。

## 切换与验收

1. 隔离验证通过后，在维护窗口停止两端旧服务，确认没有遗留进程写入数据库，完成最终一致备份。
2. 根据实际 systemd 单元更新程序和独立虚拟环境路径，继续引用原有私有环境文件和数据目录；检查心伴模板中的 `__APP_DIR__`、`__ENV_FILE__` 已替换。不要直接复制未替换的模板启用服务。
3. 在现有 HTTPS server 内加入或核对心伴子路径 location，保留心电 `/` 和 `/api/`。`nginx -t` 成功后才 reload；不把两个 Python 端口直接开放到公网。
4. 启动服务，核对进程工作目录和命令实际指向新版本。分别检查心电 `/health`、心伴 `/heartlife/api/v1/health`，以及 `/heartlife/release-source.json` 与发布 SHA 一致。健康接口成功只能证明对应服务存活，不能单独证明前后端版本一致。
5. 使用浏览器核验心电与心伴导航、登录、退出、权限边界及本次功能；确认旧前端缓存没有残留。1／3／5 分钟测量、上传、分析和报告需另记实际设备验收结果。

失败时停止新实例并保留故障日志，按部署前验证的兼容方案恢复旧程序和配置。涉及数据库时先隔离和保全升级后新增的数据，再决定迁移或恢复；不要直接用旧备份覆盖新记录。

## 部署记录

生产记录与包中的 `prepared-not-deployed` 状态分开保存；不修改包内清单来伪造已部署状态。至少记录：负责人、北京时间、完整源码 SHA、整包 SHA256、旧版本、三个组件实际路径和版本、依赖环境、两端健康结果、网页与设备验收结果、回退方案及未完成项。备份位置、私有配置与原始日志保留在服务器私有运维记录中。

确认实际切换成功后，再更新仓库的版本与交付状态；服务器未登录、备份未核验、仅打包或仅 CI 成功时，均不能登记为已部署。

## 本地打包核验

在干净的同一提交上构建前端，再运行打包校验（以下为 Bash）：

```sh
cd heartlife/frontend
npm ci
VITE_BASE_PATH=/heartlife/ VITE_RELEASE_SHA="$(git rev-parse HEAD)" npm run build
cd ../..
python tools/package_system_release.py --check
```

`--output` 可输出候选包。此命令仅验证内容和一致性，不核验所有者或 main 质量证据；生产交付使用上面的所有者手动工作流。
