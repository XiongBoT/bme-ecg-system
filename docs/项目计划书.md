## 一 项目概述

本项目面向课程研究与工程验证：由 STM32 采样，树莓派完成显示、处理与本地保存，云端统一管理用户、设备、记录及分析任务，手机和电脑共用访问入口。

云端独立 QRS/RR、账号与数据库管理、统一管理后台、任务中心与人工复核、心电健康助手已完成源码合并。公开数据实验已扩展到三种 QRS 的完整记录比较及固定分类模型独立评测；下一步补齐实采、性能和客户端验收，并按实际授权安排部署。无线接入作为后续扩展，先比较手机中转和设备直连两条路线，再选择一条进行原型验证。各阶段以本计划中的验收条件作为完成依据。

### 最终使用效果

用户申请并获得账号及设备授权，选择 1／3／5 分钟或在终端手动测量并查看总结；数据上传后，在手机或电脑回看波形、云端分析和历史记录，导出数据或报告。多台设备分别服务不同用户；断网保留已保存记录，恢复后补传。

## 二 目标与功能需求

基础版覆盖树莓派采集、云端管理和手机电脑访问。以下需求以可观察的使用结果为验收对象，保留现有 N/S/V 三分类和原始记录格式。

| 编号 | 目标 | 最终效果 |
| --- | --- | --- |
| F01 | 连续采集与原始记录 | 按既定 360 Hz 协议接收、保存原始 ADC、来源和无效标记；异常段可定位，波形可回看。 |
| F02 | 完整测量流程 | 待机不创建记录；确认使用者、端口与存储后开始；支持手动、1 分钟、3 分钟及 5 分钟，结束保存并显示总结。 |
| F03 | 端侧显示与识别 | 显示波形、心率、信号质量和现有心搏分类；界面操作不阻塞采集，暂停显示不停止保存。 |
| F04 | 云端统一管理 | 支持历史搜索、筛选、备注、回收站恢复、数据导出及持久后台分析；刷新页面不丢失任务。 |
| F05 | 多设备与账号隔离 | 设备独立凭据、授权名单和状态；普通用户仅访问自己的记录；管理员可查找和创建账号、重置密码、停用/恢复及撤销登录，保留记录与归属。设备停用和凭据轮换生效。 |
| F06 | 手机与电脑访问 | Windows、Android 与浏览器共用云端账号和记录，能够查看波形、总结、分析结果与下载状态。 |
| F07 | QRS RR 与 HRV | 保留完整 R 峰序列与有效片段，提供 RR 统计；仅在正常窦性间期可信时输出相应 HRV，缺失有明确原因。 |
| F08 | 断网与异常恢复 | 已保存数据断网可保留并补传，重复上传不增点、不改归属；失败任务可重试，重启后可恢复。 |
| F09 | 可复现实验与交付 | 形成准确性、时延、内存、稳定性与容量报告，提供模型量化对照及后续实机功耗证据。 |
| F10 | 数据库维护与服务器备份 | 管理员查看元信息、整理回收站、统计占用、检查完整性并在服务器保存一致备份；无网页备份下载，恢复只写新目录并撤销旧凭据。 |
| F11 | 心电健康助手 | 登录页申请由管理员审核；主动选择记住账号/密码；日/月/年趋势、APP 设置和 1/3/5 分钟固定时长测量；报告注明实际数据范围。 |
| F12 | 工作流与人工复核 | 本人任务中心、默认关闭的上传后自动分析、复核标记/备注/过期提示；管理员运行问题不泄露他人波形。 |
| E01 | 后续无线接入 | 比较 STM32 经手机中转与经 Wi-Fi 模块直连云端两条路径，选定路线完成独立原型。 |

### 范围与约束

沿用现有 AD8232、STM32F103C8 与 Raspberry Pi 2 配置，云端保持主要平台。Android 采用现有应用继续完善，iPhone 以网页/PWA 访问为基础。房颤识别、新模型训练、原生 iOS 应用和大规模商业化接入不纳入本轮基础交付。外壳和外观为可选项。

账号继续使用现有账号密码登录，微信登录按用户决定暂不实现。管理员管理普通账号的权限边界保持不变，不新增管理员读取他人记录的能力。

模型 N 类不能自动等同于经过确认的正常窦性间期。没有可信 NN 条件时只提供 RR 变异性；不生成疾病诊断、健康评分或未经验证的压力等级。

## 三 系统方案与数据流程

### 系统组成

| 层次 | 主要职责 | 边界 |
| --- | --- | --- |
| 采集层 | AD8232 获取信号，STM32 定时采样并输出数据帧 | 保持采样节奏；标记来源与无效值 |
| 终端层 | 串口接收、波形、质量检查、端侧推理、测量总结、原始落盘和上传 | 采集与保存不依赖持续联网 |
| 云端层 | HTTPS 接口、账号及设备校验、记录存储、分析队列和版本化结果 | 服务端决定权限；不信任客户端自报归属 |
| 访问层 | Windows、Android、手机浏览器与电脑浏览器 | 展示同一账号的数据；状态清楚，失败可恢复 |

### 基础数据路径

当前模块关系及手机测量时序见[系统架构与数据流](系统架构.md)，本章保留计划层面的约束。

AD8232 → STM32 → 串口 → 树莓派本地记录 → HTTPS 上传 → 云端存储与分析 → 手机或电脑查看。

采集侧沿用 360 Hz、115200 波特率、7 字节帧与现有块记录约定。原始数据不被滤波结果或分析结果覆盖；所有派生结果关联记录编号、输入摘要、算法版本和参数。不同设备的同名记录不得相互覆盖。

### 一次测量的完整过程

- 准备：确认获授权账号、端口、空间与时长；取消时不创建记录。

- 采集：保存原始数据并显示波形与质量，明确标记数据来源和异常片段。

- 结束：到时或手动停止，保存后显示统计；缺少可靠数据时标为未知。

- 上传与分析：按块确认、重试和去重；校验归属后，由持久后台任务分析。

- 查看与导出：同一账号跨端回看；区分保存、上传和分析状态，导出标明来源与版本。

### 权限与数据管理

管理员维护用户、设备和授权，不因管理身份自动取得他人波形访问权。普通用户只访问自身记录；设备只使用自己的凭据上传。退出、换号、换设备或换记录时，迟到响应不能覆盖当前界面。真实记录、账号库、凭据及私钥不进入 Git 或公开报告。

## 四 算法深化与实验设计

### 云端结果接入

复用现有检测器与质量门控，把完整 R 峰、RR 连续段、有效覆盖与排除原因接入云端后台分析。结果独立保存为带版本的派生数据，保留旧模型结果及原始输入；算法升级可重新分析，不静默覆盖旧报告。前端展示任务状态、有效时间、样本数和缺失原因。

先接入有依据的 QRS/RR 指标。HRV 仅在正常窦性间期条件成立时计算；证据不足时显示“暂无符合条件的 HRV”，保留 RR 统计。NN 判定策略须单独验证后启用，不以 N 类预测直接替代。

上述 QRS/RR 接入、结果版本和 HRV 缺失原因展示已在 PR #26 完成软件验证；可信 NN 生成策略、扩大验证集及实采效果仍需后续工作，不能据此宣布完整 HRV 功能或临床有效性已完成。

### 公开数据实验

- 保存已完成的 10 条记录各 5 分钟基线；新增全长报告已完成 44 条非起搏记录 QRS 比较和 21 条分类独立评测（上游 DS2 排除与训练记录 201 同人的 202），见[完整报告](algorithm-validation/算法对比与分类评测.md)。后续扩展仍须记录选择规则、开发使用情况与独立验证边界。

- 冻结算法版本、参数、通道、幅值映射与匹配容差后运行。若根据某条记录修改算法，该记录转为开发依据，不再声称其为独立验证。

- 报告 QRS 的 TP、FP、FN、灵敏度、阳性预测值、F1 和 R 峰定位误差；RR 只比较双方相邻且处于同一有效连续段的间期。

- 单独分析复杂节律与噪声导致的失败，包含已发现的 207 号记录的困难片段；同时报告覆盖与拒绝情况，避免只统计成功片段。

- 分类报告提供各类别 precision、recall、F1、macro-F1 与混淆矩阵；公开标注验证和真实采集展示分别记录。

### 性能评估与量化对照

分别测量读取、QRS/质量门控、推理、排队、接口响应和结果生成耗时。记录硬件、依赖、输入规模、重复次数及预热方式，报告中位数、P95 和峰值内存；并发负载从小规模递增。

课程深化保留 FP32 与 INT8 对照任务：使用同一数据和标签，报告精度差异及运行表现。先核对 ARM32 运行路径与算子支持，再进行转换；若受限，记录明确阻碍和替代方案。树莓派耗时、真实功耗和服务器容量必须在相应设备上测量，本机结果只作为开发基线。

### 分析阶段退出条件

独立验证结果可由记录清单和命令复跑；已知异常场景有测试或明确限制；云端及手机页面能说明哪些指标有效、哪些未计算；结果与输入、参数和版本可以追溯。

### 本地负载试验建议

先用 1、2、5、10 个模拟上传客户端逐级测试，固定单设备数据量、块大小和请求节奏，观察错误率、接口 P95、队列长度和内存趋势。并发档位是实验条件，不是系统支持规模承诺；不得把同一台开发电脑上的结果直接称为公网服务器容量。

建议安排不少于 30 分钟的本地连续合成输入，并注入网络中断、任务失败、服务重启和账号切换。时长属于本计划建议的工程检查值，不是课程原定评分标准。准确率和性能的正式目标值在冻结基线后单独确定，不虚构已达到的指标。

## 八 后续无线接入方案

本方案在基础链路验收后实施，不计入当前软件阶段的交付条件。STM32F103C8 不集成 Wi-Fi 或蓝牙无线收发能力，需要外接模块；型号、存储和供电在原型前确定。[S1]

| 比较项 | 方案 A 手机中转 | 方案 B 设备直连云端 |
| --- | --- | --- |
| 路径 | STM32 → BLE 模块 → Android App → HTTPS → 云端 | STM32 → Wi-Fi 模块 → 路由器或热点 → HTTPS → 云端 |
| 预期效果 | 手机连接采集设备、显示并缓存数据，再利用手机网络上传 | 采集设备在有 Wi-Fi 时直接上传，手机和电脑仅负责查看 |
| 新增工作 | BLE 协议、扫描配对、权限、断连恢复、缓存和上传；现有网页容器需新增原生能力 | 无线配网、设备认证、TLS、分块上传、重试和断网存储；评估 ESP32 类模块 |
| 主要限制 | 依赖手机蓝牙、进程存活及后台策略，系统权限与锁屏行为需实测 [S3]、[S4] | 依赖可用 Wi-Fi 与足够存储；HTTPS 能力取决于模块及固件配置 [S2] |
| 适用方向 | 需要手机随身操作、现场无固定网络的便携场景 | 希望减少中转设备、以云端为中心的固定或热点接入场景 |

### 共同协议与可靠性要求

采样与无线发送解耦。当前数据帧约为 360 点/秒 × 7 字节 = 2.52 kB/秒，3 分钟约 454 kB，未计无线开销。缓存由手机或模块端持久存储承担并明确上限，不能仅依赖 STM32 SRAM。以上为设计估算，需实测吞吐。

封包定义版本、绑定设备、会话、连续序号、有效标记和内容校验，配套确认、重传及缓存满处理。蓝牙配对不能替代云端授权；手机不得伪造设备身份，TLS 应校验证书，设备凭据独立可撤销。

### 后续实施顺序与退出条件

W1 可行性比较预计 2–3 个工作日，选定路线、模块与协议后再估算 W2 原型工期。先以合成数据验证分包和重传，再接入 STM32；验收覆盖 3 分钟连续传输、断连恢复、点数与摘要、账号隔离。无线距离、续航和容量由实测确定。

方案 A 首先验证 Android，iPhone 蓝牙采集另行评估。方案 B 可采用 UART 驱动 ESP-AT，或由无线模块承担完整上传逻辑，需核对固件功能及缓存能力。[S2]

优先复用已有 STM32、AD8232、树莓派、显示器、服务器及开发环境。双机验收需要第二台独立采集终端；安卓手机、另一台 Windows 电脑、Wi-Fi/移动网络和功耗仪表按阶段协调。无线模块优先借测，型号确定后再列采购清单。服务器续费、存储和新增硬件费用按实际资源核算，本文不虚构价格或已获预算。

| 风险 | 影响 | 应对与退出依据 |
| --- | --- | --- |
| HRV 资格不足 | 错误使用 N 类结果会产生不可信指标 | 保留 RR 结果；NN 条件不足则未知；验证资格策略后才启用 HRV。 |
| Pi 2 资源与 ARM32 限制 | 模型性能或量化运行受限 | 提前做引擎兼容与基准；保留 FP32 基线，记录实际瓶颈。 |
| 串口 网络或存储异常 | 记录缺失、上传重复或保存失败 | 采集保存解耦、显式缺口、幂等上传、空间检查及故障恢复测试。 |
| 并发与授权竞争 | 记录越权或凭据撤销不及时 | 服务端事务内核对身份；覆盖停用、换号和迟到响应。 |

| 文档与发布状态失配 | 用户拿到旧包或误认为已上线 | 源码、标签、包摘要、部署版本分别登记，统一更新日志。 |
